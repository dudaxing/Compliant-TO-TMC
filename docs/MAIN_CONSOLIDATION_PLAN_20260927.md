## 3. main 目前需要修复的三件事

### 3.1 当前交付清单已经失效

本轮直接读取 Git blob，重新核对当前清单的全部 2437 项：2435 项匹配，`README.md` 和 `.gitignore` 的大小/SHA 不匹配。main 跟踪 3018 个文件（含清单自身），另有 **580 个载荷文件未进入清单**，包括后续 P1、稳定 F 和 v4 内容。

`handoff/repository_manifest.json` 仍是 S0 的 `32af6c40…`。这不是仅供阅读的历史清单：`tools/handoff.py` 的默认 `verify` 会核对它，`prepare-replay` 又先调用 verify 并按清单复制文件。因此当前入口会因两项失配拒绝；仅更新两项哈希仍会漏掉新增文件。

处理方式：保留旧 S0 清单原字节及身份；针对最终 main 重新生成当前交付清单，并检查“全部跟踪载荷＝主树清单覆盖”，同时保留声明的外置资产层。不能直接采用独立复核分支按旧树生成的清单，也不能取消哈希校验。

### 3.2 当前入口混合了多个时期的状态

README 顶部已有 v4 通过记录，后文仍出现“新内核尚未实现”“稳定 F 计划未执行”；`RESUME_DEVELOPMENT.md` 还把 P1 前置修复列为接续首项。这会使接手者重复工作或使用过期入口。

处理方式：新增一个当前状态入口（建议 `docs/CURRENT_STATUS.md`），统一更新 README 和接续指南的当前区；把原 v3 叙述明确标为截至 2026-09-21 的历史记录。旧冻结报告和带历史日期的 `DEVELOPMENT_CONTEXT.md` 保留原结论，通过新的状态入口连接。新的入口同时写清 v3 失败、v4 有限通过、三项制造场失败、默认内核未切换及 HF5 未实施。

### 3.3 新科学资产还不能仅靠远程仓库完整恢复

现有 11 个历史/S0 Release 资产的元数据匹配，但以下两包未进入公共资产索引，当前记录只声明本机位置：

建议沿现有公开科学证据边界发布为固定版本的 Release 资产，保留原包哈希，提供第二处经核验副本并接入统一资产索引及依赖。新增外置内容不包括历史排除的 MATLAB/论文原件。空目录下载、还原、成员哈希和绑定核对通过后，才能称“另一台电脑可完整接续”。本轮只核对现有元数据和记录，没有下载这两包或重新执行恢复。
